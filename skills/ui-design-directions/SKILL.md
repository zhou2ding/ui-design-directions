# UI 设计方案对照

用户要求更新案例库时，直接按[收录规则](references/update-cases.md)处理。本次只需调研时，交付到研究笔记即可。设计任务按下面的顺序推进。

## 1. 先看产品，再选参考

打开实际页面或用户提供的截图，确定用户最常做的事、已有的功能、需要覆盖的设备，以及哪些内容允许变动。已有回答直接沿用。记录一个代表性任务及其结果，留一张原始界面作对照。若用户要保留布局，把导航、栏宽、面板位置、按钮顺序和业务流程列为固定项。

从[产品与界面案例](references/cases.md)和[X 作品](references/x-cases.md)里挑与问题有关的作品。优先研究用户指定的主参考。以 Apple 为主时，官网先看产品页，客户端先看同类控件。Human‑MD 这类补充参考，只有在某个做法确实适合当前产品时才采用。从图库发现作品后，打开作品详情或作者的实际页面。

## 2. 用逆向 Skill 把观察做实

按[工具目录](references/tools.md)运行 `taste`。官网至少观察首屏、一个具体功能段落和小屏版本。客户端观察与任务有关的工具栏、主内容和一个实际状态变化。保存代表性截图，对照实测的字号、颜色用途、边缘、阴影或视口变化。公开页面上嵌着的产品截图只能提供视觉证据，截图内的按钮无法从外层网页读取 CSS。

研究每个采用的案例时写下四件事，包括页面或状态、观察到的细节、它解决的具体问题，以及这个产品可以怎样借鉴。例如，Pages 在讲模板时放大选择器。介绍编辑器时，可以先给一张足以辨认工作区的全景，再把一次关键操作放大到文字清晰的程度。向用户附上实际参考过的链接。在聊天或独立研究笔记中给出处，方案图内留给产品本身。

## 3. 选择设计 Skills，制作四个方向

从工具目录中指定一项主设计 Skill，再为当前薄弱处选辅助项并说明用途。复用同一组功能、同一份样例和同一视口，各方案可以公平比较。素材优先使用清晰的真实界面。用演示数据时，在交付说明里标明，并保留近似真实任务的密度、单位、图例和结果。

**允许调整页面结构时**，先给四个方向各画一张无色草图。以一款数据工具为例，可以让访客沿一项任务从输入走到结果、按目录跳到不同功能、拖动参数查看图表变化，或并排核对一次操作前后的差异。选择适合实际产品的四种读法。比较首屏的视觉重心、中段的结构和访客下一步做什么。如果去掉颜色和主图后仍像同一页，重画重复的方案。

**只允许美化现有界面时**，让四图中的任务、内容、布局和缩放完全一致。让区别体现在控件体系上。例如同一组工具按钮可以围绕精细描边、分段底板、实体按压或半透明材质展开。每个方向都要把字重、圆角、边缘、阴影、选中态组合成一致的规则。四版都展示同一个菜单或选区的局部近照，核对透明层上的文字和键盘焦点是否清楚。

官网用真实任务组织文案与配图。概览回答「有哪些能力」，下方的场景演示回答「怎样完成一项工作、得到什么」。写能适用于多种输入的功能说明，把具体论文、商品或项目名称留在示例界面里。保留产品自身的标识、术语和识别度。

## 4. 交付四张大图，等待选择

在独立预览目录制作效果图。可以渲染临时 HTML/CSS 原型或使用制图工具。真实产品截图承担界面细节，生成图可用于专门的主视觉。网页方案至少展示首屏和有代表性的下拉内容。客户端方案展示同一整窗和关键控件细节。涉及动效时补上前后状态或短片，让静态图也能说明用途。

在一个可滚动的对照页或消息里直接展示 A、B、C、D 四张大图，按阅读宽度排列，窄屏逐张纵排。让用户无需点击、切换或打开下拉框就能看到每版。每图旁写一句差别及其适合的场景。在交付前实际打开导出的预览，按常用屏宽检查文字、细节、图片清晰度和按钮遮挡。

**交付到这里就停。** 请用户选 A/B/C/D，或明确指定要组合的部分。「先讨论」「还想看看」均表示继续留在预览。用户要求再出一轮时保留已有方案，按反馈增加或替换指定的预览。选定前，正式项目的源码和部署都保持原状。

## 5. 选定后再开发

按选定版本列出需要调整的组件、样式与必要素材，在授权范围内实现。按相同数据、视口和交互状态，对照预览与成品。官网检查首页、关联页面和窄屏按钮。客户端检查主要工作区、弹窗、焦点和选中态。明确哪些结果来自浏览器模拟，哪些来自实际设备或安装版。
